# Development and Evaluation of the Integrated Framework {#sec:ch8}

## Introduction

This chapter answers the fourth research question: whether the conventional methods and the ML model can be brought together in one system that returns exactly the offline results, quickly enough for interactive use. It describes the architecture of the framework (@sec:f-arch), the Simulink operating model and its verification (@sec:f-sim), the diagnosis service (@sec:f-service), the dashboard (@sec:f-dash) and the end-to-end test bench, with its fidelity and response time (@sec:f-bench).

## Architecture {#sec:f-arch}

The framework connects three parts, each built in the environment best suited to it (@fig:framework in Chapter 3):

- the **Simulink operating model** of a transformer, which provides the load, temperatures and insulation ageing at any moment of a simulated period and marks the moments at which an oil sample is taken;
- the **conventional methods**, programmed in MATLAB, which interpret the gases of a record; and
- the **diagnosis service** in Python, which holds the released ML model and returns its diagnosis to any program that sends it the five gases.

The **dashboard**, built with MATLAB App Designer, brings the three together on one screen. The parts exchange only three kinds of information: the identifier of a record, the five gas concentrations in ppm, and the fault classes coded 0 to 6. No gas value ever passes through the Simulink model.

## Simulink Operating Model {#sec:f-sim}

### Structure of the Model

The model represents a 40 MVA, 110/20 kV, oil-immersed power transformer with forced-air cooling. It is built by a MATLAB script, so that every block, parameter and connection is recorded and the model can be rebuilt exactly, and all parameters are named variables in one parameter script (@tab:simparams). The electrical data are those of a standard 40 MVA, 110/20 kV transformer type of the pandapower library (Thurner *et al.*, 2018), and the thermal constants are the default values of an open-source implementation of IEC 60076-7; they describe a typical unit, not a specific nameplate.

[[TABLE:sim_params]] {#tab:simparams}

@fig:simtop shows the top level of the model as it appears in MATLAB R2025b. It has eight subsystems:

- **SS1 Grid supply:** a three-phase 110 kV source;
- **SS2 Power transformer:** a two-winding 40 MVA, 110/20 kV transformer block;
- **SS3 LV measurement:** measures the secondary current and computes the load factor *K*;
- **SS4 Variable load:** a load whose demand follows a load profile;
- **SS5 Losses to heat:** converts the load and no-load losses into heat inputs;
- **SS6 Thermal network:** solves the IEC 60076-7 equations (@eq:topoil to @eq:theta-h) as thermal resistance–capacitance circuits;
- **SS7 Outputs and ageing:** computes the hot-spot temperature, the ageing rate and the logged outputs; and
- **SS8 Sampling events:** marks the times at which an oil sample is taken.

![Top level of the Simulink operating model in MATLAB R2025b. Blue: Simscape Electrical network (SS1–SS4); green: Simulink arithmetic (SS5, SS7); orange: Simscape thermal network (SS6); purple: DGA sampling events (SS8). Blue lines are physical connections and black lines Simulink signals](12_Thesis/figures/simulink_top_level_blocks.png){#fig:simtop width=15.5}

SS1 to SS4 form a Simscape Electrical network and SS6 a Simscape thermal network. The electrical network uses Simscape's frequency-and-time formulation, which accepts only linear equations, so the non-linear arithmetic of SS5 and SS7 is done with ordinary Simulink blocks; the model is therefore a combination of Simscape physical networks and Simulink arithmetic. @fig:ss6 shows the thermal network. The diagrams of all the other subsystems are given in Appendix A.

### Model Checks

The model was checked with the Simulink Model Advisor, which ran 132 modelling and Simscape checks: 120 passed, 11 gave warnings, 1 could not be completed by the tool and none failed. The check that could not be completed (bus signal names) was replaced by a direct test, since the model contains no bus. The 11 warnings concern style rules for control software and options for code generation, which do not apply to a simulation model of this kind, and each was recorded with its reason. Problems found by the checks were corrected in the build script; for example, a deprecated square-root block was replaced and several diagnostics were set to report errors.

### Verification against the IEC 60076-7 Equations

The model passed every verification check (@tab:simver and @fig:simver). Against the independent solution of the IEC 60076-7 equations, the largest difference after the first 10 min was {{sim_t1_emax_oil}} K for the top-oil and {{sim_t1_emax_hs}} K for the hot-spot temperature at rated load, and {{sim_t2_emax_oil}} K and {{sim_t2_emax_hs}} K in the load-step test. All four are far inside the 0.1 K limit. The 63 % rise time of the top-oil temperature differed from *k*~11~*τ*~o~ = 75 min by only {{sim_rise_diff}} min. At rated load from a 20 °C ambient, the top-oil temperature settled at {{sim_t1_oil}} °C and the hot-spot temperature at {{sim_t1_hs}} °C.

[[TABLE:simulink]] {#tab:simver}

![Verification of the Simulink thermal model against an independent solution of the IEC 60076-7 equations: (a) rated load from a cold start, (b) load step from 0.6 to 1.2 pu at 6 h; upper panels: temperatures, lower panels: difference between model and reference with the ±0.1 K tolerance](12_Thesis/figures/thesis/simulink_verification.png){#fig:simver width=15.5}

One finding of the verification is worth noting. With the default solver tolerance (relative tolerance 10^-3^), the hot-spot difference reached about 0.1 K, so that a small change in the solver's time steps could move it across the limit. The tolerance was therefore tightened to 10^-4^, after which the difference was about one-tenth of the limit. This shows the value of verifying a simulation against an independent solution rather than assuming that the solver's default settings are adequate.

### Operating Scenarios

Three illustrative operating scenarios were simulated: constant rated load for 24 h, a daily load cycle and a short overload (@fig:scen-daily and @fig:scen-over; the rated-load scenario is in Appendix B).

![Daily load-cycle scenario (last of three simulated days): load factor, temperatures, and relative ageing rate with the loss of life](12_Thesis/figures/thesis/scenario_daily.png){#fig:scen-daily width=15}

![Short-overload scenario: 1.3 pu for 2 h on a base load of 0.8 pu](12_Thesis/figures/thesis/scenario_overload.png){#fig:scen-over width=15}

Under the daily cycle, which rises from 0.5 pu at night to 1.0 pu at the evening peak, the hot-spot temperature peaked at {{sc_daily_hs}} °C in the evening and the loss of life over the day was {{sc_daily_L}} h, much less than the 24 h of a day at the reference temperature. Under constant rated load the hot-spot temperature settled near {{sc_rated_hs}} °C, slightly above the 98 °C reference, and the loss of life was {{sc_rated_L}} h in 24 h. The 2 h overload of 1.3 pu raised the hot-spot temperature to {{sc_overload_hs}} °C, and that day's loss of life of {{sc_overload_L}} h was greater than that of a day at constant rated load. These figures show the operating context that the dashboard displays next to each diagnosis. They are illustrative, because the scenarios are not measured load profiles and the thermal constants are default values.

### DGA Sampling Events

Subsystem SS8 marks the moments at which an oil sample is taken (6, 12, 18 and 22 h of a simulated day in the demonstration). A Simulink signal is numeric, so SS8 outputs the number of sampling events passed. Outside the model this number selects the identifier of the next held-out record, and the dashboard reads that record's measured gases from the data file. The parameter script reads only the record identifiers and data roles, so no gas value enters the model's workspace. An automated test confirmed that no block, parameter or logged signal of the model refers to a gas concentration.

## Diagnosis Service {#sec:f-service}

The released ML model is served by a web service written with the FastAPI framework (@tab:api). A program sends the five gas concentrations, and optionally a record identifier, as a JSON message to the address 127.0.0.1:8000, and the service returns the predicted class, the probabilities of all seven classes, the confidence, and the name, version and SHA-256 fingerprint of the model.

[[TABLE:api_fields]] {#tab:api}

Four design choices make the service safe to use:

- **Strict input checks.** Every gas is required and must be a finite number not below zero, and unknown fields are refused, so that a misspelt gas name cannot be ignored silently. Invalid requests receive HTTP status 422, "unprocessable content" (Fielding, Nottingham and Reschke, 2022), with the field and the reason.
- **Model integrity.** The model is loaded once at start-up only after its SHA-256 fingerprint has been checked; if the file has changed, the service refuses to start.
- **Exact answers.** The probabilities are returned unrounded, so that they can be compared exactly with the offline results.
- **Local use only.** The service listens only on the local computer; it is a test bench, not a networked product, and has no user authentication.

Twenty-one automated tests cover input validation, the answers, the start-up check and the published description of the interface.

## Diagnostic Dashboard {#sec:f-dash}

The dashboard (@fig:dashboard) is the part of the framework that an engineer sees. It loads a DGA file, computes the three conventional diagnoses with the MATLAB functions, sends the five gases to the service, and shows all four answers side by side with the class probabilities, the sample in the Duval Triangle and an agreement lamp. The lamp is green when all three conventional answers agree with the ML class, amber when at least one does not, and grey when the service cannot be reached. A conventional answer agrees with the ML class when it is the same class; the IEC dual answer D1/D2 agrees when the ML class is D1 or D2; DT and no-diagnosis answers never agree.

![The diagnostic dashboard after a simulated day with four DGA sampling events (record IECTC10_0001 of the IEC TC 10 database). The **Run Simulation** button (1) runs the Simulink model for a simulated day and plots the top-oil and hot-spot temperatures as operating context (5). At each sampling event the dashboard looks up the record whose identifier the model provides, diagnoses it, and lists it in the event table (9) with the simulated hot-spot temperature at that moment. In the example of @fig:dashboard, record IECTC10_0001 is diagnosed as partial discharge by the ML model with a probability of 0.92. IEC 60599 and the Duval Triangle agree, but the Rogers method gives no diagnosis, so the lamp is amber. The engineer sees at once that the methods do not all agree and can look more closely at the sample.

## End-to-End Test Bench {#sec:f-bench}

### The Test Run

For the formal evaluation, a test bench ran the integrated system over all {{n_heldout}} held-out records. The unchanged Simulink model was simulated with one sampling event every 15 min, about 97 h of simulated time in all. For each event the bench called exactly the functions that the dashboard uses, without drawing, and logged the answers and the response time (@fig:testbench). The ML classes given at the events were {{tb_ml_classes}}. All three conventional methods agreed with the ML class on {{tb_agree3}} records ({{tb_agree3_pct}}), and none agreed on {{tb_agree0}} ({{tb_agree0_pct}}), which shows again how often the methods differ on real records.

![Test-bench run over the 388 held-out records: (a) simulated hot-spot temperature and the sampling events; (b) ML diagnosis of the record taken at each event; (c) number of conventional methods that agree with the ML diagnosis](12_Thesis/figures/thesis/testbench_run.png){#fig:testbench width=15.5}

### Fidelity and Response Time

@tab:integration gives the fidelity and response time, and @fig:resp shows the response time of every request.

[[TABLE:integration]] {#tab:integration}

The integrated system returned exactly the offline ML class for all {{int_F}} records (fidelity F = 1), with all seven probabilities identical, and the three conventional answers were identical to the offline results for every record. No call failed. The response time of the service had a median of {{int_med}} ms and a 95th percentile of {{int_p95}} ms (range {{int_min}} to {{int_max}} ms), far below the target of 1 000 ms. Without the first five "warm-up" calls the values were almost the same ({{int_med_nw}} and {{int_p95_nw}} ms). Both requirements of the fourth research question were therefore met.

The complete processing of one record, including the three conventional diagnoses in MATLAB and the agreement check, took a median of {{int_tot_med}} ms. {{int_tot_over1s}} of the 388 records took more than 1 s in total, the longest {{int_tot_max}} ms; most of this time was spent in MATLAB, not in the service. The time for the whole record was reported for information only, because the requirement concerns the service request.

## Discussion

Several recent studies have moved from classification experiments towards systems, such as digital twins with online diagnosis (Yao *et al.*, 2024), data fusion on monitoring platforms (Cui *et al.*, 2025) and probabilistic prognostics from DGA sensor data (Kashiwagi *et al.*, 2025). These systems seldom show the conventional diagnosis that engineers already trust next to the ML answer, and they seldom report whether the deployed system reproduces the offline results on which its accuracy claims rest. The framework of this thesis does both. Its fidelity of 1 over all held-out records is a necessary condition for trusting a deployed model, because any error introduced by the deployment, such as a different pre-processing, a rounded input or a changed model file, would otherwise go unnoticed. The fingerprint check and the strict input validation make such errors visible.

The response time of under 100 ms at the 95th percentile on an ordinary laptop shows that the service is fast enough for interactive use; the main delay of the integrated system lies in the MATLAB part, which could be reduced if needed. The Simulink model was verified to well within its tolerance, but it represents a typical transformer with default thermal constants and illustrative load scenarios; its temperatures provide context for the diagnosis and are not used to make it.

## Summary

An integrated framework was built in which a verified Simulink model of a 40 MVA transformer provides the operating context, MATLAB functions compute the conventional diagnoses, a FastAPI service provides the ML diagnosis, and a MATLAB App Designer dashboard shows them side by side with an agreement lamp. Over all {{n_heldout}} held-out records the system reproduced the offline diagnoses exactly (fidelity 1) with no failed call, and the 95th-percentile response time of the service was {{int_p95}} ms, well below the 1 000 ms target. The fourth research question is therefore answered positively.
